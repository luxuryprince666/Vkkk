# Полная автоматизация: архитектура v2 (по итогам разбора площадок)

Документ опирается на `research/free-nakrutka-2026.md` — там факты по каждой площадке (капчи,
таймеры, пулы, мёртвые домены). Здесь — как из этих фактов собрать софт, который работает сам.

Коротко, что меняется по сравнению с v1 (`docs/goal-automation-plan.md`):

| Было (v1) | Стало (v2) |
|---|---|
| цели считают ёмкость по «идеальным» лимитам | ёмкость считается **с учётом класса площадки**: таймеры, пулы, капчи, «держите вкладку» |
| заход = открыть страницу, человек жмёт | заход = **драйвер площадки**: знает, куда вставить ссылку, чего ждать, что считать успехом |
| сбой сайта → брейкер | сбой → **переезд на резерв + самопроверка живости форм** |
| качество не обсуждалось | в модель добавлено понимание: бесплатно = боты/офферы, и это пишется в интерфейсе |

## 1. Слои системы

```
┌──────────────────────────────────────────────────────────────────────────┐
│ ЦЕЛИ      «100 лайков + 200 просмотров к 12.11»                          │
│           ёмкость, вердикт, план, прогресс, ETA, пересчёт                │
├──────────────────────────────────────────────────────────────────────────┤
│ ПЛАНИРОВЩИК  раскладка по площадкам и времени                            │
│           приоритет: ядро (A/B без капчи) → таймерные → пул → капчевые   │
├──────────────────────────────────────────────────────────────────────────┤
│ ОЧЕРЕДЬ   tasks (как сейчас): due_at, статусы, атомарный claim           │
├──────────────────────────────────────────────────────────────────────────┤
│ ДРАЙВЕРЫ  по одной на площадку: как именно сделать заказ                 │
│           + generic-драйвер для «обычной формы»                          │
├──────────────────────────────────────────────────────────────────────────┤
│ РОБОТ     Playwright: ввод «по-человечески», ожидание таймеров,          │
│           определение капчи, скриншот, подтверждение результата          │
├──────────────────────────────────────────────────────────────────────────┤
│ НАБЛЮДАТЕЛЬ  прогноз, живость площадок, деградация, автопочинка плана    │
└──────────────────────────────────────────────────────────────────────────┘
```

Смысл разделения: **знание о площадке** (какая форма, какой таймер, какая капча) живёт отдельно от
**умения водить браузер**. Когда площадка переделает вёрстку, ломается один профиль, а не весь софт.

## 2. Знание о площадках: `research/sites.json` → `site_profiles` в базе

Профиль площадки — то, что мы выяснили живьём:

```json
{
  "id": "smmnakrutka",
  "automation_class": "B",
  "registration": false,
  "captcha": [],
  "hold": "таймер 5 минут",
  "page_must_stay_open": false,
  "obstacles": ["лимит: только первые 10 запросов в сутки", "таймер 5 минут"],
  "order_page": {
    "link_selector": "input[placeholder*='ссыл']",
    "submit_selector": "button:has-text('Заказать')",
    "wait_seconds": 300,
    "success_text": ["заказ принят", "успешно", "ожидайте"],
    "fail_text": ["лимит", "попробуйте позже", "неверная ссылка"]
  },
  "quota": {"cooldown_min": 5, "daily_claims": 10, "pool": null},
  "checked_at": "2026-11-10"
}
```

Правила эксплуатации профилей:

- **generic-драйвер** умеет работать без профиля: ищет поле по подсказкам (`placeholder`/`name`
  содержит «ссыл», «url», «link», «http»), кнопку — по тексту «заказать/получить/отправить».
  Им покрыто 8 из 10 форм (см. `order_page_fields` в `sites.json`).
- **самопроверка раз в сутки**: открыть 1–2 страницы заказа, проверить, что поле и кнопка на месте,
  капча не появилась. Не совпало — площадка помечается `degraded`, задачи на неё не планируются,
  в интерфейсе «Проверить вручную».
- **капча не «ошибка», а свойство**: если в профиле `captcha != []`, площадка уходит в класс C и
  получает отдельное окно в плане (см. §5).

## 3. Модель данных (миграция до v4)

```sql
CREATE TABLE goals (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    target_id    INTEGER NOT NULL REFERENCES targets(id) ON DELETE CASCADE,
    title        TEXT,
    deadline_at  INTEGER NOT NULL,
    pace         TEXT NOT NULL DEFAULT 'human',   -- human | max | quiet
    status       TEXT NOT NULL DEFAULT 'draft',   -- draft|planned|running|paused|done|failed
    created_at   INTEGER NOT NULL,
    closed_at    INTEGER,
    note         TEXT
);

CREATE TABLE goal_items (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    goal_id      INTEGER NOT NULL REFERENCES goals(id) ON DELETE CASCADE,
    metric       TEXT NOT NULL,               -- likes|views|followers|plays|reposts|comments
    need         INTEGER NOT NULL,
    have_before  INTEGER NOT NULL DEFAULT 0,
    planned      INTEGER NOT NULL DEFAULT 0,
    done         INTEGER NOT NULL DEFAULT 0,
    status       TEXT NOT NULL DEFAULT 'open'
);

ALTER TABLE tasks ADD COLUMN goal_id INTEGER REFERENCES goals(id) ON DELETE SET NULL;
ALTER TABLE tasks ADD COLUMN metric  TEXT;

-- что мы знаем про площадку (кладётся из research/sites.json при старте)
CREATE TABLE site_profiles (
    site_id       TEXT PRIMARY KEY REFERENCES sites(id) ON DELETE CASCADE,
    automation    TEXT NOT NULL DEFAULT 'C',      -- A | B | C
    captcha       TEXT NOT NULL DEFAULT '[]',     -- JSON-массив
    hold_seconds  INTEGER NOT NULL DEFAULT 0,
    keep_open     INTEGER NOT NULL DEFAULT 0,
    pool_daily    INTEGER,                        -- общий пул на всех (SMMPrime)
    profile_json  TEXT NOT NULL DEFAULT '{}',     -- селекторы, тексты успеха/провала
    degraded      INTEGER NOT NULL DEFAULT 0,     -- форма не совпала → выключено
    checked_at    INTEGER NOT NULL DEFAULT 0
);
```

Обратная совместимость сохраняется: одиночная накрутка через мастер живёт как раньше (`goal_id IS NULL`).

## 4. Планировщик: как выбирается площадка под заход

Приоритет — не «где больше за раз», а «где сейчас безопасно и предсказуемо»:

| Приоритет | Класс | Почему | Примеры |
|---|---|---|---|
| 1 | **A** — форма без капчи, без таймера | нет риска застрять, человек не нужен | Nakruti.net |
| 2 | **B** — без капчи, но таймер/ожидание | надёжно, просто дольше | SMMnakrutka, DoctorSMM, SMM8, Masslike |
| 3 | **C** — капча или общий пул | дорого по времени человека | PRSkill, SMM.media, LowcostSMM, SMMCode, SMMPrime |
| — | выключены | не работают/сломались | feijoa, bestsmm (домены мертвы), 777like |

Внутри класса — жадно по объёму, но с тремя ограничителями:

1. **Скорость на объект.** Не больше N единиц в час на конкретную ссылку со всех площадок сразу
   (по умолчанию 60, настраивается). Это то, что реально видит ВК, а не разбивка по сайтам.
2. **Человеческий ритм.** Между любыми заходами 1–3 минуты, раз в 1–2 часа пауза 15–40 минут,
   ночью тишина (рабочие часы 8–23).
3. **Запас ёмкости.** Если площадка класса C попадает в план — её заход всегда «не последний»:
   рядом держится запасной вариант класса A/B, потому что капча может съесть 5 минут ожидания.

Раскладка по времени (функция `pace`): шаг = `срок × 0.7 / число_заходов`, но не больше 3 часов,
с джиттером ±40%. Если план упёрся в срок — режим «впритык» (плотнее и с большими объёмами).
Прототип этой математики уже работает: `tools/goal_planner.py`.

## 5. Драйверы: как делается заход на конкретной площадке

Общий контракт (реализуется один раз, дальше — только профили):

```python
class Driver:
    def open(self):        ...   # перейти на страницу заказа конкретной услуги
    def fill(self, link):  ...   # вставить ссылку (посимвольно, с паузами)
    def pre_submit(self):  ...   # дождаться таймера/очереди, если он есть
    def submit(self):      ...   # нажать кнопку
    def wait_result(self): ...   # дождаться подтверждения или капчи
    def verdict(self):     ...   # ok | captcha | quota | bad_link | site_broken
```

Реальные сценарии, которые драйвер обязан уметь (все — из проверки площадок):

- **Обычная форма** (Nakruti, SMM8, Masslike, DoctorSMM): поле → кнопка → текст «заказ принят».
- **Таймер перед заказом** (SMMnakrutka 5 мин, LikeBoom 2 мин, SMMPrime 30с→5мин): дождаться,
  не закрывая страницу; прогресс показывать в интерфейсе («осталось 3:12»), а не «зависло».
- **Очередь показа** (SMM.media, SMMCode ~37 сек): дождаться и убедиться, что заказ ушёл в очередь.
- **«Не закрывайте вкладку»** (LowcostSMM): держать окно до подтверждения, только потом закрывать.
- **Капча** (PRSkill/Turnstile, LowcostSMM/reCAPTCHA, MRPOPULAR/hCaptcha): определить, отдать окно
  человеку, ждать до `captcha_wait_sec`, при неудаче — вернуть задачу в очередь и пометить сайт.
- **Лимит исчерпан** («первые 10 запросов в сутки»): распознать текст отказа, поставить площадке
  `quota_exhausted` до полуночи и **перепланировать остаток на другие площадки**.

Если селектор не найден — `site_broken`: площадка уходит в `degraded`, план пересчитывается, в
интерфейсе появляется «Nakruti.net: форма изменилась, проверьте» — это лучше, чем тихо долбить
мёртвую страницу.

## 6. Имитация человека: конкретика

| Что | Как | Зачем |
|---|---|---|
| Пауза между заходами | 1–3 мин, джиттер ±40% | не выглядеть скриптом, не собирать капчу |
| Порядок площадок | случайный внутри класса | не «всегда Nakruti первым» |
| Перерывы | 15–40 мин раз в 1–2 часа | ровный, «живой» график |
| Часы | 8–23, настраивается | ночью никто не крутит |
| Ввод ссылки | посимвольно, 40–120 мс на символ | обычная проверка на ботов |
| Мышь | плавное перемещение к кнопке, пауза 200–600 мс | то же |
| Окно | размер/локаль/UA из набора, случайно | меньше поводов для флага |
| Браузер | один заход за раз, без параллельных окон | панели это тоже считают |
| Лимит на объект | ≤ N единиц в час со всех сайтов | главный сигнал для ВК |
| Плотность | не больше 6 заходов в час в «человеческом» темпе | «успеть любой ценой» отключает |

Важно не переиграть: главный ограничитель — **лимиты площадок**, «человечность» лишь снижает шанс
капчи. Поэтому режимы: `human` (по умолчанию), `max` (плотно, без перерывов), `quiet` (≤ 2 захода в час).

## 7. Отказоустойчивость: матрица «что сломалось → что делаем»

| Отказ | Реакция |
|---|---|
| Капча на площадке | окно человеку → ждём → решили: продолжаем; не решили: задача в очередь, сайт помечен |
| Таймер не дождались / страница закрылась | повторная попытка через 90 с, потом площадка на паузу 30 мин |
| Селектор не найден (редизайн) | `degraded` площадки, пересчёт плана, уведомление в журнал и в интерфейс |
| Сайт отвечает 5xx/таймаут | 3 неудачи → пауза 6 часов (брейкер уже есть), план переезжает на резерв |
| Лимит площадки исчерпан | `quota_exhausted` до полуночи, остаток цели → другие площадки |
| Общий пул пуст (SMMPrime) | площадка выпадает из плана, ёмкость пересчитывается с коэффициентом 0.3 |
| Домен умер (как feijoa/bestsmm) | самопроверка выключает площадку, задачи не создаются |
| ВК списал часть накрутки | недобор виден в прогрессе; цель добирает из резерва (если разрешено в настройках) |
| ПК выключили | восстановление `running → ready` (есть), пересчёт прогноза на старте |
| Отстаём от графика > 20% | автоматический `replan`: плотнее, другие площадки, при необходимости продление |
| Дедлайн прошёл | статус `failed` + честный отчёт «получилось N из M, вот почему» |

Все реакции пишутся в журнал (`events`) с одной строкой причины — чтобы через день было видно,
почему план поехал.

## 8. Что сможет софт после этого (и с какой скоростью)

Реальная пропускная способность на текущем каталоге (по прототипу, при 15 рабочих часах):

- **Ядро без капчи** даёт 25–40 заходов в час: Nakruti (10 мин × 7 услуг), SMMnakrutka (10 в сутки),
  DoctorSMM, SMM8 (30 мин), Masslike, Spetsnakrutka.
- **100 лайков** — 2–4 захода, ~20–40 минут.
- **200 просмотров** — 2–3 захода, ~15 минут.
- **500 просмотров** — 4–6 заходов, 1–1,5 часа.
- **1000 подписчиков за сутки** — невыполнимо бесплатно ни на одной площадке (потолок 300–500).
- **Капчевые площадки** добавляют ещё до 30% ёмкости, но каждое включение — ожидание человека.

## 9. API и интерфейс (что добавится)

```
POST /api/goals/preview   → вердикт с учётом классов площадок и пулов
POST /api/goals           → создать цель (создаёт задачи)
GET  /api/goals/<id>      → прогресс, ETA, блокеры, «кто сейчас работает»
POST /api/goals/<id>/replan | pause | resume | extend
GET  /api/sites/health    → состояние площадок: жива/деградировала/капча/пул/лимит
POST /api/sites/<id>/check → прогнать самопроверку формы вручную
```

В интерфейсе — две новые вещи:

1. **Карточка цели** с честной строкой про качество: «бесплатные подписчики — это боты/масса,
   отписки нормальны; живых из РФ бесплатно не бывает».
2. **Экран «Площадки»**: таблица «работает / капча / таймер / суточный лимит / проверено», кнопки
   «Проверить сейчас», «Отключить». Это то, чего сейчас не хватает: пользователь видит, на чём софт
   реально едет.

## 10. Этапы внедрения

| Этап | Что | Критерий готовности |
|---|---|---|
| **M1** | профили площадок в базе + самопроверка форм + экран «Площадки» | мёртвые/сломанные площадки не попадают в план, видно почему |
| **M2** | цели: preview → создание → прогресс (математика из `goal_planner.py`) | «100 лайков к дате» работает, вердикт совпадает с расчётом |
| **M3** | драйверы A/B-класса + робот с ожиданием таймеров | 5 площадок ядра крутятся без человека |
| **M4** | капча-сценарий в потоке цели + переезд задач на резерв | капча не валит цель, а тормозит один заход |
| **M5** | наблюдатель: прогноз, деградация, автопересчёт | отставание > 20% лечится само |
| **M6** | проверка факта (счётчик на странице), отчёты «сколько реально висит» | видно недобор/списания |

## 11. Чего этот софт не будет делать (честно)

- Не обещает «живых из РФ» — их бесплатно не существует.
- Не проверяет факт в ВК на этапе M5: считает заказанное и подтверждённое.
- Не обходит капчу автоматически: только человек в окне (так и задумано — это безопаснее для аккаунта).
- Не крутит одну ссылку быстрее безопасного темпа, даже если «успеть любой ценой»: лимит на объект
  остаётся.

## Состояние реализации (обновлено)

| Этап | Что это | Статус |
|------|---------|--------|
| M1 | Профили площадок + самопроверка форм + экран «Площадки» | **готово** |
| M2 | Цели: «сколько и за какой срок» → план заходов → прогресс | **готово** |
| M3 | Драйверы площадок: 4 движка со стенсом + curl_cffi, вердикты, память селекторов | **готово** |
| M4 | Очередь заходов по площадкам с учётом таймеров и пулов | частично (кулдауны + цели) |
| M5 | Отчёты и графики по целям | не начато |
| M6 | Мультиплатформы (TG, Instagram, YouTube) | не начато |

### Что реализовано в M1

`core/probe.py` — общий зонд (один и тот же код у CLI `tools/probe_sites.py` и у софта):
`fetch / text_of / fields_of / buttons_of / analyse / probe`; определяет капчу (recaptcha, hcaptcha,
turnstile, smartcaptcha, image-captcha, cloudflare), поля, кнопки, таймеры, SPA, iframe, антибот-блок.

`core/profiles.py`:
- `seed_profiles()` — апсерт `research/sites.json` в таблицу `site_profiles` (повторный вызов безопасен,
  ручные пометки `degraded` не перетираются);
- `_hold_of()` — из текста профиля достаёт **ожидание**, а не время доставки
  («таймер 5 минут» → 300 с, «выдача 3 мин – 1 час» → 0);
- `check_site()` — открывает страницу заказа и выносит вердикт
  `ok | js | changed | dead`; **деградация только после двух провалов подряд**, чтобы случайный
  сетевой сбой не выключал рабочую площадку;
- `health()` — таблица для интерфейса: статус, класс, капча, таймер/пул, когда проверяли;
- `is_usable()` — планировщик не ставит заходы на сломанные площадки.

`SiteChecker` в `core/server.py` — фоновая нить: раз в 30 минут берёт одну «просроченную» площадку
(не проверявшуюся сутки) и тихо проверяет форму. По одной, без параллельных запросов.

API: `GET /api/sites/health`, `POST /api/sites/check`, `POST /api/sites/check_all`.

### Что реализовано в M2

`core/goals.py`:
- `preview()` — считает **ёмкость** площадок под срок: рабочие часы, кулдаун, суточные лимиты,
  общий пул, класс площадки (C и пуловые — с коэффициентом), уже сделанные сегодня заходы.
  Вердикты: `feasible` (с запасом) / `tight` (впритык) / `impossible` (максимум меньше нужного);
- `_plan_slots()` — жадно раскладывает заходы: сначала класс A, потом B, потом C; уважает кулдаун
  услуги, суточный лимит, рабочие часы и «человеческий» интервал (70–200 с);
- `_stretch()` — растягивает план на 70 % срока (но не реже, чем раз в 3 часа), остальное — запас;
- `create()` — создаёт цель и **обычные задачи** (`tasks.goal_id`, `tasks.metric`), поэтому работают
  все прежние предохранители: брейкеры, капча, восстановление после падения;
- `progress()` — прогресс по метрикам, ETA, блокеры (сломанная площадка, капча в режиме «Без капчи»),
  заметки (капча решается в окне);
- `pause / resume / replan / extend / remove`, `on_task_done()` — прогресс обновляется после каждого
  закрытого захода; если по метрике не осталось заходов — цель пересчитывается сама.

API: `GET /api/goals`, `GET /api/goals/<id>`, `POST /api/goals/preview`, `POST /api/goals`,
`POST /api/goals/<id>/{pause,resume,replan,extend}`, `DELETE /api/goals/<id>`.

### Что реализовано в M3

`core/stealth.py` — слой движков: Patchright, Camoufox, Nodriver, Playwright + curl_cffi.
Единый адаптер `Page` (goto/js/text/shot/wait + «человечные» type/click/mouse), поэтому логика
драйвера не зависит от движка. Приоритет: patchright → camoufox → nodriver → playwright.
`LAST_TRIED` хранит, что пробовали и почему не вышло, — это видно в интерфейсе.

`core/drivers.py` — сам драйвер: `discover()` (снимок формы через JS: поля, кнопки, капча,
таймеры, iframe), `pick_link_field/pick_count_field/pick_submit_button`, `type_human`,
`_wait_for_ready` (ждёт именно кнопку, а не текст про время), `read_verdict` (приоритеты:
bad_link → captcha → ok → quota → need_human), `remember/forget` (память селекторов
в `site_profiles.profile_json.driver`), `run()` (полный заход или сухой прогон),
`run_nojs()` (форма без браузера через curl_cffi), `probe_site()` (сухая проверка площадки).

Вердикты: `ok | captcha | quota | bad_link | need_human | site_broken`.
Исполнитель (`executor._apply_driver_result`) превращает их в состояния задач: `quota` — отложить
на час, `captcha` — отдать человеку (или пропустить в режиме «Без капчи»), `site_broken` — брейкер,
`bad_link` — закрыть с причиной.

API: `GET /api/browsers`, `POST /api/browsers/install_hint`, `POST /api/sites/<id>/robot_check`,
`POST /api/tasks/<id>/robot`. Настройки: `browser_backend`, `order_email`, `nojs_enabled`.

Стенд для тестов: `tests/fake_panel.py` (8 страниц-двойников) + `tests/test_drivers.py` (39 тестов).
